# Maintain a verification skill

A feature map rots the moment the app changes. This skill is the upkeep loop for a skill generated by `/create-verification-skill` (or any project-local verification skill with a feature map). It is codebase-health work, like `/improve-codebase-architecture`: run it when you have a spare moment, or after a stretch of `/implement` tickets touched user-facing behavior. The unit of rigor is the feature, not every sentence: cover every feature file from source and exercise every feature live.

## Outcomes

Pick one, and say which:

- **clean**: every feature got source and live coverage; nothing worth shipping.
- **changed**: one commit (or one PR, if the repo works through PRs) ships proven doc, harness, or map corrections.
- **blocked**: coverage could not finish or a proven fix could not ship safely. Say exactly what blocked it.

## Edit scope

Only edit the verification skill's own directory (its SKILL.md, features/, and any harness scripts it owns). Never edit product code during a run: a behavior the map describes that the app no longer does is either doc drift (fix the map) or a product regression (report it, don't paper over it in docs).

## Pass

0. **Locate the target.** Find the project-local skill whose body has launch/drive sections and a feature map (`.claude/skills/verify/`). Several candidates → ask which one; none → stop and point at `/create-verification-skill`.
1. **Index hygiene.** Read the feature map README and list its sibling files. Fix missing, extra, duplicate, or dead entries.
2. **Source wave.** One read-only sub-agent per feature file, launched concurrently. Each explains "how does this user-facing feature work?" from source, flags likely doc drift with citations, and returns one concise live-verification recipe. Sub-agents never drive the app and never edit files. Return shape: feature summary / source entry points / likely drift or none / one recipe.
3. **Reconcile.** Every feature file has a returned summary. Merge overlapping recipes into as few app states as practical. Spot-check cited drift; don't re-prove clean claims. Sweep recent churn (`git log` since the map last changed) for user-facing surfaces missing from the map, and require a concrete source path before calling one missing.
4. **Live pass.** Required even when source looks clean. You own all driving; follow the verification skill's own launch model. Exercise every feature at least once, and hold three invariants: (1) doctor before first drive and again after any failed or surprising drive; reset or relaunch rather than hoping; (2) evidence captured so far survives every cleanup, checked at its named location; (3) nothing a drive started outlives that drive's usefulness. A doctor failure caused by skill drift is drift: fix it under edit scope and retry once before calling the pass `blocked`. A feature that can't be reached is `verified-unreachable` only with the concrete prerequisite and the route attempted. Any harness fix gets re-driven live before it ships.
5. **Triage.** Wrong or missing user-POV description → doc drift, fix it. Working behavior the harness can't drive → harness gap, fix it. App behavior that's actually broken → product gap: record it for the user and keep it out of this change; if they want it tracked, it's an issue for `/triage` (or `/diagnosing-bugs` if it's hard).
6. **Ship or stop.** For changed: re-read every changed file, then one commit or PR of proven corrections. For clean or blocked: report the outcome and the coverage honestly.

Keep concise run notes (features covered, unreachable prerequisites, confirmed drift, outcome) in a scratch location; don't commit them.
